01Mission: automatic AI review of every PR

The review engine itself is excellent — immutable diffs, prompt-injection fencing, verdict parsing, GitHub comment publication all exist and work. What's missing is the spark: nothing ever starts a review on its own.

GAP  Reviews are manual-only today

PR opened on GitHub→ worker polls every 2.5 s→ PR row updated in DB→ …sits unreviewed…→ admin clicks "AI review"→ verdict → GitHub comment ✓

The only enqueue site is the admin route (server.ts:1079). Fix is small: when the sync pass sees an open PR whose head SHA has no review yet, auto-enqueue pr.ai_review keyed by pull_request_id:head_sha. New push ⇒ new SHA ⇒ automatic re-review; same SHA ⇒ skipped. Add an auto_review_enabled toggle to ai_review_settings.

BUG  "Review & merge" never merges

mode="review_and_merge" is consumed exactly once — to retarget the PR's base branch before reviewing (worker.ts:1209). The approved verdict goes nowhere. Worse, the base gets changed even when the review rejects. Fix: move the base change after an approved verdict, then enqueue github.merge_pull_request pinned to the reviewed head SHA so the existing policy gate still applies.

BUG  Valid reviews thrown away by strict verdict parser

If the model's output contains more than one fenced JSON block (e.g. it quotes the format inside findings), parsePrReviewVerdict discards a fully-completed review as ambiguous_verdict (pr-review.ts:50) and the row is terminal — retrying can't recover it. Scan blocks last-to-first instead.

RISK  Sync loop hammers the GitHub API

Every open PR re-syncs every 2.5 s; each deep sync costs ~6+ REST calls (reviews, checks, statuses, collaborator permissions). A few open PRs ⇒ thousands of calls/hour against the 5,000/h limit → permanent rate-limit churn. Add per-PR backoff + one cheap list call per project per pass to detect changes before deep-syncing.

After the two P1 fixes: new PR → AI review queued automatically → verdict posted as a GitHub comment → approved PRs merge through the policy gate. Zero clicks.

02Mission: merging branches into other branches

The GitHub merges-API path works, but every guardrail around it is missing or lying to you.

BUG  Conflicts and failures show as "Merged ✓"

Merge form→ API returns { job }→ UI checks result.outcome — never present→ alert("Merged X into Y.") — always

ui.ts:346 tests a field that only exists in the worker's audit payload. A conflicted, refused or crashed merge reports success. Fix: persist {outcome, sha} onto the job (new result_json column), poll it from the UI, surface terminal states honestly.

GAP  No guardrails — and dedup defeated

head/base are any non-empty strings (server.ts:1178): typos become confusing failures, and merging straight into master bypasses the entire PR policy pipeline. The idempotency key embeds randomUUID(), so double-clicks enqueue duplicate real merges, and a lost HTTP response makes the retry merge again. Fix: ref-name regex + confirm flag for default-branch targets, deterministic keys (project:head:base), record-intent-before-call replay safety.

GAP  Conflicted branch merges dead-end silently

{outcome:"conflict"} lands in an audit row nobody reads. No notification, no UI state, no remediation. Offer the escape hatch that already exists: auto-open a head→base PR (GitHub's merges API can't resolve conflicts; the PR + AI conflict-resolution flow can).

BUGS  Merge-path correctness

mergeBaseIntoWorktree labels every error as "conflicted" (git-runner:333) — AI resolution then runs against a clean tree. recordProviderRefusal can downgrade an attempt already merged (pr-merge.ts:108). require_fresh_policy_binding defaults false: until flipped, the legacy squash-merge path skips required-checks/review verification entirely. And a late-detected merged PR force-completes even admin-closed tickets.
