# Nexus audit report — 2026-09-06

> Read-only code and operations audit. This report records evidence found in the supplied audit notes; it does not claim a penetration test, complete runtime coverage, or that any application fix was applied.

## Executive readout

The consolidated audit contains **39 confirmed findings**: **12 P1**, **27 P2**, and **0 P3**. Conditional risks and follow-up items remain separated below and are not included in those totals.

The most visible user-facing break is the image path: an uploaded screenshot can be stored successfully, then return 404, remain download-only, or disappear from the ticket submission (`WEB-01`–`WEB-04`). Even when the ticket stores the attachment, planning and execution currently receive no usable image evidence (`WF-09`). The next highest risks are cancellation races, worker stalls, unbound deployment evidence, migration upgrades, and artifact/restore handling.

### Intended workflow

A public report should preserve each declared upload, validate and atomically claim it, show the image to the administrator, and pass a controlled read-only reference into planning and execution. Approved work should retain its evidence and exact commit while validation, publication, provider actions and production promotion report truthful, recoverable state. The flow diagram in the HTML companion shows these handoffs.

The repair order should start by restoring the complete image-evidence path and then clearing worker liveness, cancellation and validation failures that can strand work or make the system appear healthy while it is not. Next, pin deployment evidence to the commit that will actually be deployed and make migration, artifact, restore and promotion paths retry-safe. Then repair operator truth, form validation, test safety, dependency coverage, state reconciliation and diagnostics. P1/P2 labels remain the source reviewers’ priorities; this order does not raise a finding’s severity.

## Recommended repair order

1. **Restore the complete image-evidence flow.** Make uploads retrievable, visible on tickets, atomically validated/claimed, and available through controlled read-only references to planning and execution (`WEB-01` through `WEB-05`, `WF-09`).
2. **Restore worker progress and truthful cancellation.** Address the AI provider dispatch gate, cancellation races, unbounded validation, stream-write failures, shutdown classification, queued-attempt reconciliation, cancellation of exposed run types and the canonical ticket cancellation path (`WF-01`, `WF-03` through `WF-05`, `WF-08`, `WF-10`, `WF-11`, `WEB-08`).
3. **Make deployment and promotion evidence commit-bound and time-bounded.** Fix PostgreSQL timestamp handling, repeated-poll timeout resets, moving-branch evidence, unrelated workflow selection, registry deadlines, retry dedupe, migration upgrades, shared artifact reconciliation, restore-drill recording and failed-release retries (`INT-01` through `INT-03`, `INT-07` through `INT-09`, `OPS-1`/`OPS-3`/`OPS-4`/`OPS-5`).
4. **Make operator truth and form boundaries reliable.** Add sign-out and real worker health, validate published forms and direct edits, and repair the remaining ticket UI boundaries (`WEB-06`, `WEB-07`, `WEB-09`).
5. **Make test safety and coverage trustworthy.** Isolate the E2E wrapper before relying on it, then repair fresh-database seeding and CI coverage; review the conditional dev-tool dependency exposure (`WEB-10` → `WEB-11`/`WEB-12`, `WEB-13`).
6. **Reconcile state and preserve operator evidence.** Repair close/ticket synchronization, notification diagnostics, prompt/project import semantics, global prompt deactivation, publication retries and busy-worker maintenance (`INT-04` through `INT-06`, `WF-06`, `WF-07`, `OPS-2`, `OPS-6`, `OPS-7`).
7. **Keep conditional risks visible.** Decide policy and add targeted validation before promoting follow-up items to confirmed defects.

<a id="int-01"></a>
### INT-01 — P1 — Reproduced: production workflow discovery rejects actual PostgreSQL timestamps

Source audit: **Integrations, promotion and notification** (`nexus-integrations-audit.md`). Evidence signal: **reproduced provider mock**. Qualitative effort estimate: **S** (S=localized, M=multiple layers/compatibility, L=cross-layer or high-risk; no calendar promise).

Location: `packages/github-provider/src/actions.ts:30`; caller `apps/worker/src/provider-jobs.ts:330`; DB schema `packages/database/migrations/056_deployment_management.sql:36`; default pg pool `packages/database/src/index.ts:6`.
Actual: `run.created_at >= filter.createdAfter` compares an ISO string to a JavaScript Date supplied by pg for `production_releases.created_at`. Numeric coercion produces NaN for the ISO string, so every run fails the filter. Expected: a production workflow created after the release is discovered and its jobs determine healthy/failed status.
Trigger/repro: imported the real `findWorkflowRun` with fetch mocked locally to one run at 12:01. `createdAfter: "2026-09-06T12:00:00Z"` returned run 1; `createdAfter: new Date("2026-09-06T12:00:00Z")` returned null. No DB type parser override exists in database package.
Impact: Actions promotions cannot finish normally; dashboard run/job details stay missing and release single-flight can remain occupied. Root: untyped SQL row crossing a string-only timestamp boundary.
Minimal remedy: accept Date|string and compare epoch milliseconds, or normalize the SQL value to ISO before calling.
Regression acceptance: provider tests use a real Date input, plus caller test with pg-shaped row; a newer run is selected, older run excluded.

### INT-02 — P1 — Code-proven: every deployment status poll postpones the stuck-release timeout

Source audit: **Integrations, promotion and notification** (`nexus-integrations-audit.md`). Evidence signal: **code-proven + simulation**. Qualitative effort estimate: **M** (S=localized, M=multiple layers/compatibility, L=cross-layer or high-risk; no calendar promise).

Location: `apps/worker/src/provider-jobs.ts:354`, `:357`, `:378`, `:381`.
Actual: both mechanisms calculate 15-minute timeout from `updated_at`, then unconditionally reset that timestamp on every poll. Expected: an unresolved release times out after the intended fixed period, independent of observation frequency.
Trigger: request status sync every minute for a deployment that never starts/completes. A direct simulation of these assignments for 60 polls over 60 minutes still yields failed=false. Existing tests only seed updated_at older than 15 minutes and do one poll, missing the normal repeated-poll case.
Impact: unresolved release occupies `production_releases_project_inflight_idx` indefinitely, blocking promotion and rollback; also amplifies INT-01.
Minimal remedy: measure elapsed time from created_at or a dedicated started/progress timestamp; health observation must not count as progress.
Regression acceptance: advance fake clock and poll every minute for >15 minutes; both mechanisms mark failed and release the single-flight slot.

### INT-05 — P2 — Code-proven: bulk-close leaves linked tickets permanently in PR review status

Source audit: **Integrations, promotion and notification** (`nexus-integrations-audit.md`). Evidence signal: **code-proven**. Qualitative effort estimate: **M** (S=localized, M=multiple layers/compatibility, L=cross-layer or high-risk; no calendar promise).
