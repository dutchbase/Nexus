## 1. Mission #1 — automatic AI review of every GitHub PR

### 1.1 GAP: nothing triggers a review automatically 【the big one】

`pr.ai_review` jobs are enqueued from exactly one place: the admin UI route
(`apps/web/src/server.ts:1079-1118`, `action === "ai-review"`). The worker
polls `syncOpenPullRequests()` every 2.5 s and imports all GitHub PRs every
5 min (`apps/worker/src/worker.ts:1656-1670`) but **never enqueues a review**.
A PR opened by anyone on GitHub sits unreviewed until an admin clicks.

**Fix (smallest correct version):**

```ts
// apps/worker/src/worker.ts — inside the existing sync pass, after a PR is
// imported/synced and is state==='open':
const settings = (await pool.query("SELECT * FROM ai_review_settings WHERE id=1")).rows[0];
if (settings.auto_review_enabled) {
  const reviewed = await pool.query(
    `SELECT 1 FROM pr_ai_reviews r
     JOIN jobs j ON j.type='pr.ai_review' AND j.payload_json->>'pr_ai_review_id'=r.id::text
     WHERE r.pull_request_id=$1 AND r.reviewed_head_sha=$2
       AND j.status IN ('queued','running','completed') LIMIT 1`,
    [pr.id, remote.head.sha]);
  if (!reviewed.rowCount) {
    await enqueueJob({
      type: "pr.ai_review",
      payload: { pr_ai_review_id: row.id, pull_request_id: pr.id,
                 mode: "review_only", model: settings.default_model,
                 reasoning_level: settings.default_reasoning_level },
      idempotencyKey: `pr-auto-review:${pr.id}:${remote.head.sha}`, // deterministic!
      maxAttempts: 3,
    }, client);
  }
}
```

- Dedup key `(pull_request_id, reviewed_head_sha)` uses the existing
  `pr_ai_reviews.reviewed_head_sha` column (migration 041). New push ⇒ new SHA
  ⇒ automatic re-review. Same SHA ⇒ skipped.
- Add `auto_review_enabled boolean NOT NULL DEFAULT true` +
  `auto_review_mode text DEFAULT 'review_only'` to `ai_review_settings`
  (migration), expose the toggle on Operate → AI PR Review defaults
  (`apps/web/src/pages/operate.ts:81`).
- Publish verdict as a GitHub comment — already implemented end-to-end
  (`resumePrReviewPublication` → `createPullRequestComment`). Nothing new.
- Phase 2 (optional): handle `pull_request` `opened`/`synchronize`/`reopened`
  events in `webhook-server.js` (currently push-only,
  `webhook-server.js:213-216`) for instant pickup; keep polling as fallback.

### 1.2 BUG [P1]: `review_and_merge` mode never merges

`mode` is consumed once — to retarget the PR's base branch *before* the review
(`apps/worker/src/worker.ts:1209-1215`). Nothing consumes the approved verdict
to enqueue `github.merge_pull_request` (grep-confirmed). Consequences:
(a) base branch mutated even if the review rejects/errors; (b) "review and
merge" never merges.

**Fix:** move `updatePullRequestBase` to after an `approved` verdict (and audit
it); on approve, enqueue `github.merge_pull_request` with
`expected_head_sha = immutableReview.headCommit` so the policy gate in
`approveAndMergePullRequest` still applies. This also wires up the
auto-merge story for §1.1.

### 1.3 BUG [P2]: verdict parser discards valid reviews

`parsePrReviewVerdict` throws `ambiguous_verdict` if output contains >1 fenced
JSON block (`packages/domain/src/pr-review.ts:50-56`). A model quoting the
format or embedding a JSON snippet in findings gets a fully-completed review
terminalized as `error`; retries can't help because the row is terminal.

**Fix:** scan blocks last-to-first and accept the first that parses as
`{verdict, summary}`; fail only if none parses.

### 1.4 BUG [P2]: GitHub API thrash in the sync loop

Every 2.5 s the worker re-syncs *all* open PRs; each sync =
`getPullRequestPolicyInputs` ≈ 6+ REST calls (PR + protection + reviews pages
+ check-runs pages + statuses pages + N collaborator-permission lookups)
(`packages/github-provider/src/index.ts:267-371`,
`apps/worker/src/worker.ts:1656`). A handful of open PRs burns thousands of
requests/hour against a 5,000/h limit → permanent rate-limited churn.

**Fix:** per-PR backoff — skip PRs whose `updated_at_provider` hasn't changed
and whose `last_synced_at` < N minutes ago; use one cheap
`GET /pulls?sort=updated&direction=desc` list call per project per pass to
detect changes before deep-syncing individual PRs.

## 2. Mission #2 — merging branches into other branches

### 2.1 BUG [P1]: merge-branches UI always reports success

Server returns `202 {job}` (`apps/web/src/server.ts:1183`); the UI checks
`result.outcome === "already_up_to_date"` — a field that only ever exists in
the worker's *audit* payload (`apps/web/src/ui.ts:346`). Net effect: conflict,
refusal, or total failure still alerts "Merged X into Y."

**Fix (two layers):**
1. Persist the outcome where the UI can read it — add `result_json jsonb` to
   `jobs` (migration) and write `{outcome, sha}` from `runProviderJob`
   (`apps/worker/src/provider-jobs.ts:104-124`), or create a
   `project_branch_merges` table.
2. Replace the alert with a poll of `GET /api/admin/jobs/:id` and surface the
   terminal state ("Merged · sha abc123" / "Conflict — needs resolution" /
   "Failed: …"). Minimal stopgap: change the alert text to "Merge queued".

### 2.2 GAP [P1]: no guardrails on head/base; silent policy bypass

`head`/`base` are any non-empty strings (`server.ts:1178-1181`), passed
verbatim to `POST /repos/…/merges`. Typos become confusing job failures, and
nothing prevents merging directly into `master`/`main` — bypassing the entire
PR review + policy pipeline that governs PR merges. Also:
`idempotencyKey: ...:${randomUUID()}` defeats the `jobs.idempotency_key`
UNIQUE constraint — double-click = two real merge jobs; and if a merge HTTP
response is lost, `failJob` retry performs the merge again
(`packages/github-provider/src/index.ts:390-398` has no replay guard).

**Fix:**
- Validate both refs: `git check-ref-format` equivalent regex
  `/^[A-Za-z0-9._\/-]{1,200}$/` + reject `base === project.default_branch`
  unless `confirm_default_branch: true` (audited).
- Deterministic key: `github.merge_branches:${project.id}:${head}:${base}` —
  plus a client-generated request id when repeating a pair is legitimate.
- Record intent before the HTTP call; treat replay/204 as success.

### 2.3 GAP [P2]: conflicted branch merges dead-end

`mergeBranch` returns `{outcome:"conflict"}` which lands in `audit_events`
metadata and nowhere else (`provider-jobs.ts:119-124`). No notification, no UI
surface, no offered remediation. The repo has an AI conflict-resolution flow
for PRs (`pr.conflict_resolution`) but nothing for branch merges.

**Fix:** on conflict, enqueue a notification (`enqueueNotification` exists),
surface state on the project page, and offer "open an intermediate PR
head→base instead" (reuses `createPullRequest`) — GitHub's merges API cannot
resolve conflicts; a PR + existing AI conflict-resolution flow can.

## 4. Roadmap to "center for all development work"

Ordered by leverage; items marked ★ close a §1/§2 gap directly.

1. ★ Auto-enqueue AI reviews on PR open/push (§1.1) + settings toggle.
2. ★ Wire approved verdict → policy-gated merge; fix `review_and_merge`
   semantics (§1.2). After this, "new PR → AI review → comment → merge" runs
   end-to-end with zero human clicks.
3. ★ Branch-merge trustworthiness: deterministic idempotency keys, ref
   validation, outcome persistence + UI surfacing, conflict notifications
   (§2.1-2.3).
4. Stability batch: B1-B6 (process-killing rejection, retry deadlock, arg
   injection, worktree leaks/GC).
5. Sync efficiency: per-PR backoff + delta detection (§1.4); webhook-driven
   `pull_request` events as instant trigger (phase 2).
6. UX: job-outcome polling/toasts everywhere, branch pickers fed from synced
   repo data, merge preview (commit range) before Approve & merge, one-click
   `sync_one` on stale PR rows.
7. Hygiene: B10-B18, server.ts router split (~1,600-line if-chain → route
   table + modules), inline-JS externalization, prompt re-seed check.

- ★3 Branch merges: ref regex + `confirm_default_branch` guard,
  deterministic idempotency keys (hourly bucket / client request_id),
  `jobs.result_json` (migration 053) written by provider-jobs, new

  CONFLICT/failed honestly.
- Stability B1–B6: cancellation-poll try/catch, main-loop guards,
  `worktree add -B`, `assertRemoteBranchName()` at all remote-name sites,
  conflict-worktree `cleanup()` lifecycle, unified worktree root under
  `<dataRoot>/worktrees`, 10-min-delayed orphan sweep.
- Efficiency §1.4: per-PR sync floor (`DCC_PR_SYNC_MIN_AGE_SECONDS`, default
  90s) + partial index (migration 054).
- Also fixed: verdict parser multi-block acceptance, terminal-ticket coercion

  tsconfig `noEmit`, vitest excludes `.worktrees/**`, 15s testTimeout, deleted
  391 stray compiled `.js` twins.

**Audit round 2 (same day, independent reviewers):** fixed a HIGH zombie-row
bug where a terminally-failed auto-review respawned a 'running' review row
every sync pass (dedup now keys on the exact `pr-auto-review:<id>:<sha>`
idempotency key across all statuses); sweep now converges (deregisters swept
runs, prunes only when something was removed) and its patterns can no longer
match execution worktrees; auto-merge logs loudly when its idempotency key
collides with a terminal job; UI sends a fresh `request_id` when re-submitting
after a failed merge so failures are retryable within the hour; uploads got
their own quota bucket (`kind` column, migration `055`) instead of eating the
submission budget; jobs route validates full uuid shape (404 not 500);
`DCC_PR_SYNC_MIN_AGE_SECONDS=0` honored; new `merge-route-regressions.test.ts`
(4 route-level tests).

**Deliberately deferred** (with reasons):

- Webhook `pull_request` events (§1.1 phase 2) — polling pickup now ≤ ~92s;
  instant triggers need webhook-secret plumbing on GitHub first.
- server.ts router split + inline-JS externalization — zero-behavior churn
