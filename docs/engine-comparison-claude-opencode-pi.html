Execution Engine Analysis — Claude Code · OpenCode · Pi

For dev-control (ticket-in / reviewed-PR-out worker on this VPS)  ·  Should Pi join, and could it lead?  ·  Compiled Feb 2026

Bottom line up front

  1. Keep Claude Code as the main execution driver. The worker's security posture (bubblewrap sandbox, egress restriction, fail-closed) is built on claude-runner. Nothing else matches that containment story today.
  2. Pi is a good addition as a third engine — worth building. It slots into the exact pattern opencode.ts already established (--mode json ≈ OpenCode NDJSON), and its multi-provider support covers Gemini/Grok/OpenAI/DeepSeek through one CLI — useful for planning-phase cost control and provider redundancy.
  3. Pi as main driver: not yet. Prerequisites: port the scoped-bwrap launch to a pi-runner (same upgrade path already noted for OpenCode), then A/B execution quality on real tickets for a few weeks. Its minimalism is a feature interactively, but your pipeline depends on mature agentic behavior, and Pi is young.
  4. Server resources are not the deciding factor. All three are Node-family processes with similar footprints (measured below). Claude Code is the heaviest in long-running sessions; the bigger lever is token overhead, where Pi's minimal harness wins.

04Pi specifically — honest pros & cons

Where Pi genuinely helps

  • One CLI, many providers — swap models per phase without new integrations: cheap model (DeepSeek/Groq) for planning, strong model for execution, instant fallback when a provider rate-limits.
  • Subscription auth — can drive Claude Max / ChatGPT Pro / Copilot logins, potentially reducing pure-API spend for interactive admin-side work.
  • Minimal harness — 4 tools, lean prompts: lower overhead tokens per request than heavyweight harnesses; less surface for prompt confusion.
  • Clean JSON/RPC modes — maps 1:1 onto the existing opencode.ts NDJSON pattern; estimated effort to add a third engine is small (mirror one 400-line file + tests).
  • Extensible without forks — TS extensions/skills/packages; the worker could later inject project-specific tooling.

Where Pi falls short today

  • No native OS sandbox. Containment = Docker, Gondolin micro-VM extension, or wrapping the spawn in your existing bwrap machinery — i.e., the same work flagged as the OpenCode upgrade path, done twice.
  • Young & fast-moving. v0.84; event schemas and flags can shift under a headless integration. Auto-closed external contributions signal a curated, small-team project.
  • Slowest cold start (6.4 s vs ~1.3 s) — irrelevant per-run, but noticeable if the worker ever fans out many short planning calls.
  • No track record in this pipeline. Execution quality on real dev-control tickets is unknown until A/B'd; the pipeline's value is reviewed-PR quality, and that's where risk concentrates.
  • Smaller ecosystem — fewer battle-tested skills/MCP integrations than Claude Code's plugin economy.

06Recommended path

Three moves, in order

  1. Now — nothing. No engine change. Claude Code remains the execution backbone; OpenCode stays the budget lane. Both are proven in this worker.
  2. Next sprint (optional, ~1 day) — add a pi.ts third engine. Mirror opencode.ts: spawn pi --mode json, parse agent_end/message_end usage into AiUsage, hermetic env, reuse the terminate() escalation. Gate it behind the same read-only/write config split. Payoff: provider redundancy and cheap-model planning without adding another integration per provider.
  3. Only if step 2 proves out — consider Pi as main driver. Conditions: (a) port scoped-bwrap so write-mode runs are contained like Claude's, fail-closed; (b) A/B ≥ 20 real tickets Pi-vs-Claude with blind review of PR quality; (c) pin the Pi version in the worker and test upgrades before deploying, since the schema is young. Until then "main driver" status stays with the engine whose failure modes you've already paid to learn.
